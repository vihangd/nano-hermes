# nano-hermes — Compatibility, Adoption & Pi Performance Findings (2026-06-03)

## Context

You asked for four things: (1) review the latest `nanobot` and `hermes-agent` changes and keep nano-hermes compatible with nanobot, (2) adopt sensible features from hermes, (3) research other self-evolving agents for improvement ideas, and (4) confirm it runs on a Raspberry Pi 3B+ with a performance audit.

Both upstream repos were pulled (`nanobot` +9144/-3469; `hermes-agent` +128k). This document is **findings only — no code changes were made**. It records the compatibility status, a prioritized list of adoptable ideas, and the Pi performance audit, so any follow-up work can be scoped and signed off separately.

## 1. Compatibility audit — verdict: production code is 100% compatible with 0.2.1

Method: ran the nano-hermes suite twice — against installed nanobot **0.2.0** (baseline) and against the freshly-pulled upstream HEAD **0.2.1** (via `PYTHONPATH`), then spot-checked every nanobot symbol nano-hermes patches.

| Target | Result |
|---|---|
| Installed nanobot 0.2.0 | **897 passed** in 21.6s ✅ |
| Pulled nanobot 0.2.1 HEAD | 358 passed, 326 failed, 213 errors ❌ |

**The entire 0.2.1 breakage is one root cause, and it is test-scaffolding only:** `tests/conftest.py:35` does `patch("nanobot.agent.loop.Dream")`. Upstream commit `d1a94dae` ("refactor(dream): replace two-phase Dream class with simple cron + process_direct") **removed the `Dream` class** from `nanobot.agent.loop`, so the patch target no longer exists and every test using the `loop` fixture errors at setup.

Production code is unaffected — `Dream` appears in nano_hermes only in two comments (`config.py:41`, `memory/budgets.py:5`). The `install()` path never touches it.

**Every other patch point survives in 0.2.1** (verified against upstream source):
- `AgentRunner._request_model` — still at `runner.py:629`, identical signature `(self, spec, messages, hook, context)` → the runner injection patch (`cli.py:73`) is safe.
- `AgentLoop.__init__`, `_extra_hooks`, `loop.workspace`, `context.memory`, `context.skills`, `loop.tools.register`, `loop.create_task` — all present.
- `SessionManager`, `SubagentManager` (the other two conftest patches) — still imported in `loop.py:25,54`.
- `Dream`'s runtime role was replaced by `CronService` (`loop.py:71,258`), which `__init__` accepts as an injected param.

### Recommended fix (when you choose to act) — version-tolerant, supports both 0.2.0 and 0.2.1

Make the `Dream` patch in `tests/conftest.py` conditional on the symbol existing, so the suite is green on either nanobot version:

```python
from nanobot.agent import loop as _loop_mod
import contextlib

# inside _make_loop, replace the fixed `with patch(...)` stack:
with contextlib.ExitStack() as stack:
    stack.enter_context(patch("nanobot.agent.loop.SessionManager"))
    sub_mgr = stack.enter_context(patch("nanobot.agent.loop.SubagentManager"))
    # 0.2.0 has Dream; 0.2.1 replaced it with CronService — patch whichever exists
    if hasattr(_loop_mod, "Dream"):
        stack.enter_context(patch("nanobot.agent.loop.Dream"))
    if hasattr(_loop_mod, "CronService"):
        stack.enter_context(patch("nanobot.agent.loop.CronService"))
    sub_mgr.return_value.cancel_by_session = AsyncMock(return_value=0)
    return AgentLoop(bus=bus, provider=provider, workspace=tmp_path)
```

This is a **dev/CI-only** change (end users never run nano-hermes's tests). The dep pin `nanobot-ai>=0.2.0` stays as-is; no production change is required for 0.2.1. Estimated effort: ~10 lines, one file. After applying, re-run the suite under both versions to confirm green.

> Note: this conflicts with the "support both" answer only in that the *installed* venv is still 0.2.0. To actually exercise 0.2.1 in CI, add a second test job that installs upstream HEAD (or pin a 0.2.1 release once published). Until then the fix keeps the door open without forcing the bump.

## 2. Raspberry Pi 3B+ performance audit (static analysis — not measured on hardware)

**Honesty caveat:** no real Pi was available this session. This is static hot-path analysis + resource reasoning, not measured Pi latency/RAM. Hardware assumed: 1GB RAM (~600–700MB usable), quad Cortex-A53 @1.4GHz, microSD I/O.

**Headline: the "Pi-first" tenets hold up. No unbounded full-table load exists on any per-turn hot path; embedding genuinely stays off the critical turn path; no local-model dependency sneaks in.** Findings are mostly Medium/Low.

### Already done well (credit to prior pi-hardening work)
- WAL + `synchronous=NORMAL` + `busy_timeout=10000` (`session/db.py:360-365`) — best lever for SD write endurance.
- Archive commits batched once per turn, not per-row (`session/archiver.py:179-205`).
- VACUUM gated behind a 7-day cooldown (`hook.py:533-553`, `config.py:250`).
- Retention purge uses nested subqueries, not a Python-materialized `IN (?,…)` list, to dodge `SQLITE_MAX_VARIABLE_NUMBER` (`session/db.py:432-458`) — the recent `bbc3440` fix.
- Embedding scheduled as a background task; the loop never awaits the network (`archiver.py:218-226`).
- Unhealthy-provider cache fails fast (600s) instead of eating 20s×3 timeouts per call (`embedding/chain.py:46-127`).
- Shared TCP connector `limit=4` sized to the cores (`chain.py:60-68`).
- All O(N²) clustering paths capped: `distill_max_chunks=150`, `workflow_induction.max_trajectories=100`, `fts_k=25`, `vec_k=25`, `final_k≤32`.
- Deps are `pydantic, aiohttp, numpy, sqlite-vec, tiktoken` — **no torch/transformers/onnx**.

### Findings (prioritized)

**H1 — `tiktoken` encoder reconstructed on every token count.** `memory/budgets.py:27-30` calls `tiktoken.get_encoding("cl100k_base")` on every `memory_patch` budget check. First call must load the ~1.7MB BPE vocab and, if uncached on disk, may attempt a network download before falling back to a byte heuristic. *Fix:* memoize at module level (`functools.lru_cache`/lazy singleton), set `TIKTOKEN_CACHE_DIR` and ship the vocab so the Pi never hits the network. ~5 lines.

**M1 — Background vec/trajectory commits run on the event-loop thread.** `archiver.py:242-247`, `trajectory.py`, `reflect/tool.py:125` do `executemany(...) + commit()` on the loop thread (scheduled via `create_task`). A WAL checkpoint landing on a slow card blocks the *entire* loop → turn jitter. *Fix:* move these writes to `asyncio.to_thread` with a dedicated short-lived connection — the pattern already exists at `hook.py:519` (`_background_purge`). Low urgency (small batches) but the most defensible perf win.

**M2 — `GoalTracker` scans the full message list every iteration.** `coordinator/goal.py:50-74` already reduced to a single pass (commit `d1593db`), but still iterates *all* messages front-to-back and joins list-content per message → O(total transcript) per turn, O(n²) over a long `/goal` session on a weak core. *Fix:* the runtime/goal block rides in the **current (last) user message**; scan from the tail and break on first match. ~3 lines.

**M3 — `BudgetedMemory` re-encodes the whole slot text on every write** (`memory/budgets.py`). Slots are ~2KB so absolute cost is small; subsumed by the H1 memoization fix.

**L1 — `_migrate_vec0_to_cosine` materializes a whole vec table into a Python list** (`session/db.py:338-349`). One-time, at startup, tens of MB even for a multi-year DB — won't OOM. Batch the re-insert only if paranoid.

**L2 — `record_iteration_citations` does a per-iteration UPDATE+commit when reflections were injected** (`coordinator/reflection.py:314-326`). Gated, minimal under WAL. Batch at session boundary only if write-endurance becomes a concern.

**L3 — `skill_indexer._cleanup_removed` does an unbounded `SELECT id, name FROM skill_stats`** (`skills/indexer.py:217`) plus an N-query content-hash loop (`indexer.py:159`) per index refresh. Bounded by skill *count* (tens–low hundreds), so fine; fold into one query if convenient.

**Concurrency:** no pile-up risk found. Purge/curator fire once at `iteration==0`; evolution refuses to stack (`hook.py:452-463`); embed tasks held in a `set` with a done-callback. One soft gap: **no explicit cap on concurrent embed tasks** — a one-line `len(self._embed_tasks) > N` guard would harden a headless high-rate scenario. **Thread-safety is sound** (all `create_task` work on the loop's owning thread; the only cross-thread path opens its own connection).

**Top 3 by value/cost:** H1 (memoize tiktoken), M2 (goal tail-scan), M1 (off-loop commits).

## 3. Adoptable ideas from hermes-agent (scope-filtered to Pi-feasible memory/skills/reflection/retrieval)

Filtered hard: nothing requiring a local model, daemon, GPU, or >100MB RAM; nothing from desktop/Electron/gateway/web/OAuth (the bulk of the +128k diff).

### High value
- **Skill write-origin provenance + pinning.** hermes tags writes `foreground` (user) vs `background_review` (agent) and only auto-evolves agent-created skills; users can `pin` to exempt (`hermes_cli/curator.py:234`, `tools/skill_provenance.py:37`). nano-hermes's GEPA + SkillForge rewriter select candidates purely on `status='active'` + failure thresholds (`skills/rewriter.py:105`, `skills/gepa.py:155`) with **no author awareness** — a hand-authored `SKILL.md` can be silently rewritten/deprecated. *Fix:* add `origin`/`pinned` columns to `skill_stats`; set `origin='agent'` only on `propose_skill`; add `AND origin='agent' AND pinned=0` to the two candidate queries. One flag, zero Pi cost, closes a real safety gap.
- **Standing contradiction/hygiene sweep over stored memory.** hermes's `contradict()` flags fact *pairs* sharing a subject but diverging in content (`plugins/memory/holographic/retrieval.py:338`). nano-hermes's `bitemporal.py:56` only supersedes *reactively* at insert time, never audits already-stored entries. *Fit:* a background `memory_patch(action="audit")` finding pairs with high lexical overlap but low cosine on the bge-m3 vectors already stored, capped at `distill_max_chunks`. **Do not** port the HRR/holographic algebra (numpy-heavy, O(n²), out of budget).

### Medium value
- **Time-based skill lifecycle: active → stale → archived, with reactivation** (`agent/curator.py:268`). nano-hermes only deprecates on *failure rate*, so an unused-but-not-failing skill lingers in `skill_search` forever. A pure-SQL timestamp sweep at the existing session-start purge point prunes dead weight with no LLM; recency auto-reactivates.
- **Skill "umbrella" consolidation — merge sibling skills into one** (`agent/curator.py:~359-410`). nano-hermes dedups skills only at *search time*; duplicates accumulate on the SD card. LLM-driven, so gate behind `rewrite_session_interval` and reuse the embedding clusters already computed for `workflow_suggest`.
- **Pre-mutation snapshot + rollback for the evolution pipeline** (`hermes_cli/curator.py:372-461`). nano-hermes keeps per-skill `skill_versions` but has no one-shot undo for a bad GEPA+rewriter *batch*. A cheap "tarball the `skills/` dir before each evolution cycle" gives a coarse safety net.

### Low / skip
- Trust-weighted + temporal-decay *ranking* (`retrieval.py:92,569`) — overlaps existing RRF + UCB1 bandit; marginal.
- **Skip entirely:** remote memory tiers (hindsight/honcho/mem0/supermemory — daemon/SaaS), HRR holographic algebra, darwinian-evolver (50–500 LLM-call subprocess), and the curator's daemon delivery mechanism (nano-hermes already has the `after_iteration` + `rewrite_session_interval` seam — borrow the *policies*, not the process architecture).

## 4. Self-evolving agents research (2024–2026) — ranked by delta over what nano-hermes already ships

nano-hermes already has: Reflexion critique, Voyager skill library, SkillForge rewriting, GEPA prompt evolution, bitemporal invalidation, RRF+MMR retrieval, trajectory store with injection, salience nudges, contextual embeddings. "Adoptable" below = genuinely new mechanism that is Pi-clean (no local model).

### Top adoptable (highest value/cost first)
1. **Relevance/recency/frequency decay + eviction.** nano-hermes has bitemporal *invalidation* (fact became false) but no *decay* (fact is stale/unused). Add `decay_score = w_rel·sim + w_rec·exp(-Δt/τ) + w_freq·log(access_count)`; recompute in a background job; feed as an RRF tiebreaker and as the eviction key for a retention cap. Pure SQL + arithmetic; directly bounds store growth on a 1GB box. (Memory-survey line, arXiv 2505.00675.)
2. **ACE-style incremental delta-updates + grow-and-refine ("playbook").** GEPA tends to *rewrite* prompts — exactly the "context collapse" ACE warns about. Add a bullet-level table (id, content, embedding, helpful_count, harmful_count); on reflection, append/update **deltas** instead of regenerating, de-dup via vec0, prune by harmful_count + decay. Reflect step is one hosted LLM call; merge/de-dup is non-LLM. (arXiv 2510.04618.)
3. **Failure-case retrieval + K≈4 cap (CBR / Memento, non-parametric).** Trajectory store already does ~80% of this. Deltas: attach an explicit binary success/failure label and **keep failures** as cautionary cases; hard-cap injected cases at K≈4 (empirically optimal, and a free token/latency win on a Pi). (arXiv 2508.16153.)
4. **ACE helpful/harmful counters as a skill-promotion signal.** Two integer columns incremented on each retrieval+outcome, feeding the draft→active→deprecated policy and the decay score. Turns coarse success-rate promotion into a continuously-updated bandit-ish signal at zero model cost.
5. **A-MEM neighbor evolution** (update existing notes' tags/links on write) — feasible but write-heavy (extra LLM round-trip); gate strictly behind salience. (arXiv 2502.12110.)
6. **CRAFT-style create→validate→abstract→dedup** + multi-view skill retrieval (index name + docstring separately) — addresses library bloat; dedup/validate are local. (ICLR 2024.)
7. **ToolMaker-style validate-execute-repair loop at draft creation** with a small retry cap, gating promotion on a stored mini-test. (ACL 2025.)
8. **Background consolidation pass every N episodes** — run decay recompute (#1), neighbor evolution (#5), skill dedup (#6) together off the hot path; avoid aggressive write-time summarization (≈20% fact loss + SD wear).

### Infeasible on a Pi (no local model) — documented so they're not re-proposed
- **TT-SI** (test-time fine-tune — gradient step on weights) ❌
- **Memento parametric variant** (online MLP Q-reranker — live training loop) ⚠️/❌
- **Gödel Agent / SICA / ADAS** (recursive self-code-rewrite — high-risk, coarse; SkillForge+GEPA already occupy this niche safely) — skip
- **AlphaEvolve / AgentSquare** (large search budgets, many rollouts) ❌
- **Mem0 / Zep-Graphiti as a dependency** (heavy services) — borrow the idea (validity windows, already have it), not the service ❌

## 5. Suggested phasing for follow-up (requires separate sign-off per item — no work authorized by this doc)

1. **Compat (dev/CI):** version-tolerant conftest fix (§1). Smallest, unblocks 0.2.1.
2. **Pi/perf quick wins:** H1 tiktoken memoize, M2 goal tail-scan, M1 off-loop commits (§2). Small, safe, additive.
3. **Safety/hygiene (zero-LLM):** skill provenance + pinning, decay/eviction, helpful/harmful counters, time-based skill lifecycle (§3, §4 #1/#4). Highest value-to-risk.
4. **LLM-gated evolution upgrades:** ACE delta-playbook, failure-case retrieval K≈4, umbrella consolidation, snapshot/rollback (§3, §4 #2/#3). Larger; gate behind existing background scheduler.

Each item maps onto existing seams (SQLite schema additions, `after_iteration`, `rewrite_session_interval`, RRF fusion) — consistent with nano-hermes's additive, no-fork philosophy.
